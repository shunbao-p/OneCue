### 1.2 一处必须前置修正的工程债

计划 03 存在一处不影响当前成片、但不应继续扩散的明显问题：

- `程序文件/引擎/video_v2/runtime.py:26` 使用 `importlib.import_module("sub" + "process")`；
- 原因是 `tests/test_v2_job_bundle_contract.py:205-212` 对整个 `video_v2` 包做字符串扫描并禁止出现进程库名称；
- 计划 03 的 `CommandRunner` 实际仍严格使用 argv、`shell=False`、取消、terminate/kill 和测试替身，故没有形成命令注入或运行故障；
- 但以拆分字符串绕过过宽测试属于可维护性反模式。若不修，高级 Provider 会被迫复制同类写法。

因此，计划 04 批次 1 必须先做最小修正：

1. 把计划 02 的静态测试收窄为“公共输入和契约层不得提供任意命令、服务 URL、filtergraph 或 Provider 私参”；
2. 在计划 03 runtime 测试中继续严格证明 argv-only、`shell=False`、无 `os.system`、取消和旧产物保护；
3. `runtime.py` 恢复普通、可读的标准库进程模块导入；
4. 计划 01/02/03 定向测试全部通过后，方可开始任何新 Provider 实验。

这项修正不改变 Schema、公共 API、缓存语义或成片，不要求回退计划 03 PASS。

### 1.3 计划 04 必须继承的边界

- `load_job_bundle` 与 Schema v1 仍是正式任务唯一输入；
- 包 A 现有 TTS、字幕、时间线、final、三层缓存、取消、原子提交和报告不得由实验工具接管；
- 高级动态化只生产单镜头视觉候选，失败时保留 FFmpeg 版本；
- 不修改包 B、V1、两份 Schema或计划 01–03 既有样片；
- 不加入 BGM、环境音、SFX；
- 不把任意命令、模型路径、服务 URL、浏览器脚本或工具私参塞入 Job Bundle；
- 正式接入属于后续工作，本计划先用隔离实验形成取舍证据。

## 2. 计划目标

### 2.1 核心目标

1. 形成一套可复用的 Image 2 关键帧制作方法：Brief、风格板、角色表、参考图、镜头提示词、局部修订和质量门；
2. 用 6 张不重复镜头验证同一角色、服装、场景时代与统一画风的一致性；
3. 判断 MFLUX 是否值得成为无 Codex 生图时的本地静态图后备；
4. 判断 Draw Things 是否只保留为人工工具、I2V 实验入口或完全不采用；
5. 在同一组 3 张代表性图片上比较 FFmpeg、DepthFlow、HyperFrames 和可选本地 I2V；
6. 记录安装复杂度、首轮/热启动耗时、内存/磁盘、取消、残留进程、输出规格、许可证和人工准备成本；
7. 形成统一技术/视觉评分表与盲化 A/B 审片材料；
8. 对每个候选给出“正式接入候选、特殊镜头人工使用、保留研究、拒绝采用”之一的明确结论；
9. MVP 最多选择一个高级动态 Provider 进入后续接入候选；允许一个也不选；
10. 把已验证的关键帧和视觉模板交给计划 05，用于两条不同内容的端到端质量验收。

### 2.2 本阶段成功不是“全部安装成功”

本计划成功的定义是决策清楚、证据可复核，而非候选全部可用：

- Image 2 主路径形成可重复方法和一组可用的 6 镜头关键帧；
- 至少完成 FFmpeg 基线、DepthFlow 和 HyperFrames 的有界实测或有证据的早停；
- 本地图片后备与本地 I2V 都得到明确结论；
- 任何未完成实跑的候选都有具体阻塞：未获大模型下载授权、超出时间/内存/磁盘门、许可证不适合或工具接口不稳定；
- 没有为了证明工具“能用”而隐藏原始缺陷、无限调参或使用后处理伪造提升；
- 最终能回答下一阶段默认用什么、哪些镜头可升级、失败如何回退。

### 2.3 计划完成的硬结果

- 一份 `image_workflow_v1.md`：Image 2 风格/角色/分镜生图方法；
- 一份 `motion_feasibility_v1.md`：候选工具、实测、评分、许可证和决定；
- 一组 6 张不重复的 Image 2 关键帧和完整生成账；
- 一套 3 图基准集：人物近景、建筑/城门、前中后景明确的环境图；
- 每个被实跑候选的原始输出、标准化输出、日志、耗时和资源摘要；
- FFmpeg 与候选的同输入、同时长、同规格 A/B 视频和联系表；
- 用户视觉复核结论；
- 0 或 1 个高级动态 Provider 的后续接入候选；
- 不改变核心 Schema 与现有稳定 final。

### 2.4 本阶段明确不做

- 不把 OpenAI 图像 API 嵌入包 A，不要求用户提供 API key；
- 不做完全无人值守生图；
- 不训练 LoRA、DreamBooth 或自有图像模型；
- 不安装 ComfyUI；
- 不同时下载多套大型图片/I2V 模型；
- 不把 DepthFlow、HyperFrames、Draw Things 或 MFLUX打进包 A 发布包；
- 不在本阶段改 Schema v1 增加 Provider 字段；
- 不让 HyperFrames 接管整片时间线、字幕、TTS 或 final；
- 不要求本地 I2V 成为 MVP；
- 不做口型同步、复杂人物动作或长镜头连续表演；
- 不为轻微视觉差异投入无限调参；
- 不执行完整发行包构建、签名、公证、认证或 Web UI。

## 4. 决策原则与早停机制

### 4.1 四条原则

1. **先比较再接入**：正式核心不因某个 demo 好看就引入依赖；
2. **原始输出优先**：不得用强后处理掩盖脸、手、边缘或时序漂移；
3. **镜头路由而非全片绑定**：高级工具只服务适合它的少量镜头；
4. **复杂度必须换来可见收益**：若用户和评分表都看不出明显提升，保留 FFmpeg。

### 4.2 每个工具的四级结论

| 结论 | 含义 |
| --- | --- |
| `formal_candidate` | 质量、性能、取消、规格与维护门均通过，可进入后续正式 Provider 接入评估 |
| `manual_only` | 对少数镜头有价值，但准备成本、许可或接口不适合自动化，只保留人工/实验使用 |
| `research_only` | 有潜力但当前机器、版本或模型未达到门槛，保留证据，不进入 MVP |
| `rejected` | 收益不足、失败率高、耗时/资源/许可不合理，当前不再投入 |

`not_evaluated` 不是最终结论；若用户不授权大模型下载，须转换为 `research_only` 并写明“因资源授权未实测，不进入 MVP”。

### 4.3 通用早停条件

任一候选出现以下情况，记录后停止扩大实验：

- 需要修改 Schema、包 B、V1 或重写包 A 主链才能运行；
- 安装必须污染系统或与现有 A/B 运行时冲突，且无法隔离；
- 实际下载或磁盘需求超过用户批准上限；
- 一个最小样例经过一次有依据修复后仍不能运行；
- 取消后遗留不可控进程或破坏旧产物；
- 3–4 秒镜头时间明显超过本工具门槛；
- 原始输出有严重脸/手/文字/边缘/背景漂移；
- 与 FFmpeg 比较无可见提升；
- 许可证边界与未来分发方式冲突且无法保持外部可选。

早停是有效结论，不是失败。对成片和主链几乎无影响的问题只记录。

## 5. 统一实验集与评分

### 5.1 三图基准集

固定三种输入，每个候选尽量使用同一图、同一 4 秒时长、1080x1920、30 FPS：

1. `portrait`：人物近景，含头发、肩部、衣物边缘和背景层次；
2. `architecture`：城门/建筑，有明确透视、墙体与灯光；
3. `landscape`：前景物、中景主体、远景天空或山峦层次明显。

基准集优先来自本计划 Image 2 新关键帧；在新图生成前可先用计划 03 已验证的三张原图。每张保存 SHA-256、尺寸、来源和是否含参考图。

### 5.2 FFmpeg 基线

为三张图各生成：

- 一个最适合构图的计划 03 基础运镜；
- 4 秒、1080x1920、30 FPS、无字幕、无音频的视觉基线；
- 若现有镜头渲染器无法直接生成无音频实验片，可用隔离实验脚本调用已验证的 `build_motion_filter`，不得修改正式管线来迁就基准。

所有高级输出先保留原始文件，再由统一标准化步骤转成相同规格。比较不得让某一候选因码率、分辨率或时长不同占便宜。

### 5.3 技术评分

每项记录：

- 安装命令、版本、依赖文件数、模型/浏览器下载量；
- 冷启动、热启动、单镜头墙钟；
- 峰值 RSS、系统 memory pressure、swap 变化；
- 输出原始规格、标准化耗时和最终大小；
- 退出码、错误、重试；
- 取消响应时间、残留 PID 和临时文件；
- 第一次成功前的人工作业时间；
- 每个新镜头的人工准备时间；
- 工具、代码、模型许可证及未来分发边界。

### 5.4 视觉评分

每项按 0–3 分：

| 指标 | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| 主体/身份 | 严重变形或身份丢失 | 明显漂移 | 基本稳定 | 完全稳定且细节提升 |
| 边缘 | 大面积撕裂/空洞 | 明显光晕/破边 | 小瑕疵 | 稳定自然 |
| 背景/几何 | 严重扭曲 | 可见漂移 | 可接受 | 层次与空间明显增强 |
| 动作/运动 | 不自然或眩晕 | 机械/无意义 | 合理 | 与叙事和构图高度匹配 |
| 时间稳定 | 闪烁跳变 | 多处不稳 | 轻微波动 | 连贯稳定 |
| 实际收益 | 明显差于 FFmpeg | 无提升 | 小幅提升 | 一眼可见的有效提升 |

同时记录硬失败：严重脸/手错误、错误文字、水印、黑边、花屏、断帧、主体持续出界。

### 5.5 高级 Provider 通用通过门

进入 `formal_candidate` 至少满足：

- 三张基准图均能输出并标准化；
- 至少 2/3 个镜头的综合视觉得分比 FFmpeg 基线高 2 分以上；
- 用户盲化 A/B 中至少 2/3 选择高级版本；
- 无硬失败；
- 取消、失败和残留进程门通过；
- 正式适配预计不超过两个聚焦开发批次，且不改变 Schema；
- 每个新镜头的额外人工准备不超过约 10 分钟，或仅明确路由到少量 hero/design 镜头；
- 许可证允许以独立外部可选工具继续评估。

未过此门仍可为 `manual_only`；不得为凑出“高级 Provider”降低评分。

## 6. Image 2 关键帧一致性

### 6.1 定位

Image 2 是 Codex 制作阶段的主图片工具，不是包 A 内置 API。正式使用方式：执行会话通过可用的 ImageGen 能力生成/编辑图片，保存到 Job Bundle，再由包 A 校验哈希和渲染。项目不保存 OpenAI 凭据，也不假装完全自动化。

### 6.2 六镜头试验

沿用计划 03 的“雨夜信使入城”或等价短叙事，制作：

- 1 张角色基准图：面部、发型、年龄、服装、配件、色彩；
- 1 张风格基准图：时代、材质、雨夜光线、色调和画面密度；
- 6 张独立镜头：全景、中景、近景、动作姿态、建筑反应、结尾远景；
- 每张优先 9:16 构图，主体与字幕安全区明确；
- 不在生成图中放文字；
- 后续镜头尽量以少量角色/风格参考图和精确空间语言约束，不一次塞入过多参考图；
- 若某张只存在局部问题，优先小范围编辑，不全图重抽导致身份漂移。

### 6.3 生成账

每张记录：

- `shot_id`、用途、提示词版本；
- 使用的参考图顺序和角色/风格职责；
- 首次生成或编辑；
- 生成次数和被拒原因；
- 最终文件 SHA-256、尺寸与裁切；
- 人物身份、服装、场景、时代、文字、脸手与构图检查；
- 是否可直接进入 Job Bundle。

### 6.4 通过门

- 6 张均为独立构图，不再三图重复；
- 至少 5/6 张主要人物身份一眼可辨且服装/配件没有叙事性冲突；
- 6/6 画风、时代和色调属于同一项目；
- 6/6 无严重脸手畸形、乱码、水印或错误文字；
- 字幕安全区和运镜余量足够；
- 单张平均不超过 3 次生成/编辑循环；超过者记录失败模式并简化镜头，而非无限抽卡；
- 用户最终视觉复核接受这组图进入计划 05。

若其中 1 张不理想，可降级为不含主要角色的环境/物件镜头；不能用后期锐化掩盖身份错误。

## 7. 本地静态图片后备

### 7.1 MFLUX 优先，Draw Things 不重复竞争

当前只选择 MFLUX 作为本地静态图后备实测对象：

- Apple Silicon 原生、CLI 清晰；
- MFLUX 代码为 MIT；
- FLUX.2 Klein 4B 上游模型有 Apache-2.0 路线；
- 支持量化、本地模型、文本生图、图生图/编辑等能力；
- 与 Draw Things 同时做完整静态图比较会造成重复下载和维护，不符合当前“先有效、后完美”的原则。

Draw Things 静态图只做当前 CLI/许可/安装证据记录；除非 MFLUX 无法运行且用户仍要求本地后备，才重新开启静态图实测。

### 7.2 安装与模型门

执行者先：

1. 查官方当前版本与所选模型精确下载量、许可证和最低内存；
2. 建立项目外或实验目录内的隔离 uv 环境与专用模型缓存；
3. 报告预计新增磁盘、下载来源、是否需要 Hugging Face 登录；
4. 获得用户对这次大下载/安装的明确同意后才执行；
5. 不改包 A Python，不向包 A/包 B runtime 安装依赖，不改全局 `HOME`；
6. 未获授权则结论为 `research_only`，不阻塞整个计划。

### 7.3 最小实测

- 仅选一个 4B 量化模型；
- 先用 512–768 级小图验证命令、seed、输出和缓存；
- 再生成三张与 Image 2 基准集同语义图片；
- 记录冷/热耗时、内存、磁盘、seed 重现性、提示词遵循和角色一致性；
- 若支持参考图编辑，至多做一次角色参考实验；
- 不训练 LoRA，不下载第二模型补救。

### 7.4 结论门

MFLUX 成为本地后备至少需要：

- M1 Pro 32 GB 无崩溃或持续红色 memory pressure；
- 热启动单张竖屏可用图不超过约 10 分钟；
- 三张中至少两张达到“可经一次轻修进入任务包”；
- seed、版本、模型和参数可记录；
- 模型/工具许可适合本机制作；
- 不要求包 A 核心安装其依赖。

它不必超过 Image 2；只需在无 ImageGen 时提供可接受后备。若质量明显不足，可结论 `research_only`，不继续堆模型。

## 8. DepthFlow 2.5D 视差实验

### 8.1 适用范围

只面向：

- 建筑、城门、山水、街道；
- 前中后景清楚、遮挡关系相对简单的插画；
- 不要求人物真正肢体动作的环境镜头。

人物近景仍作为压力测试，但不预设它应该通过。头发、手指、衣物边缘和狭窄空隙是重点观察区。

### 8.2 隔离与许可证

- 使用独立实验环境和目录；
- 记录 DepthFlow、深度估计模型、FFmpeg/图形后端的版本；
- 优先使用许可较清楚的小型深度模型，例如 Depth Anything V2 Small；其 Small 模型为 Apache-2.0，而更大模型许可不同，不能混写；
- DepthFlow 项目为 AGPL-3.0，本阶段仅作外部本地实验；不得复制其代码进包 A，也不得打包分发；
- 若未来选择正式候选，必须保持外部可选进程并在分发前专项复核许可证。

### 8.3 实验步骤

1. 先用 CLI/doctor 或最小命令验证无头导出；
2. 只下载一个深度模型；
3. 对三图基准集各渲染 4 秒；
4. 使用同一保守运动轨迹，避免参数调优本身成为变量；
5. 保存 depth map、原始输出、标准化输出和日志；
6. 记录首次模型加载、后续热渲染、资源、取消和残留进程；
7. 与 FFmpeg 同图 A/B，重点检查发丝、肩线、城墙轮廓、天空缝隙和前景遮挡；
8. 只允许一次有针对性的参数修正，不进行镜头级长时间手绘遮罩。

### 8.4 专属门槛

- 首次安装/模型准备在用户批准范围内；
- 热状态 4 秒竖屏镜头建议不超过 5 分钟；
- architecture、landscape 至少 2 项有明显空间层次提升；
- 不出现大面积边缘撕裂、空洞或眩晕式位移；
- portrait 若失败，可以通过“路由排除人物近景”保留候选；
- Ctrl+C/取消后 10 秒内无残留渲染进程；
- 原始输出可由包 A FFmpeg 标准化。

若视觉提升成立但 AGPL/图形运行时使维护成本过高，结论可为 `manual_only`，不强行 formal。

## 9. HyperFrames 设计型镜头实验

### 9.1 正确定位

HyperFrames 从 HTML DOM 和可寻址动画渲染视频，适合：

- 标题、地图、路线、数字、档案卡；
- 多层图片、遮罩、光线、雨雪、粒子；
- 需要精确排版、设计和可重复时间轴的镜头。

它不是通用“把任意人物插画自动变成真实动作”的工具，也不替代包 A final。计划 04 只把它当单镜头视觉提供器候选。

### 9.2 技能与 CLI 约束

实际执行遵循已安装 HyperFrames 技能：

- 先确认输入和单镜头意图；
- 选择 `general-video` 或短设计型 `motion-graphics` 工作流；
- 在实际创建前运行官方技能更新步骤并读取对应技能；
- 使用项目目录、lint、snapshot/preview、render 和本机 doctor；
- Node.js 当前为 24，满足 CLI 的 Node>=22；
- 若需下载 Chromium，纳入用户下载授权和磁盘账；
- 所有动画必须 seek-safe、确定性；
- 渲染输出仅作为实验视觉片，再由包 A FFmpeg 验证/标准化。

### 9.3 三类镜头

1. `designed_info`：城门路线/警灯唤醒示意或档案卡，验证它真正擅长的设计镜头；
2. `layered_environment`：拆分天空、城墙、雨层和灯光，验证轻视差/氛围；
3. `narrative_character`：人物关键帧加保守景别运动、雨/光遮罩，验证普通叙事镜头的收益上限。

不得为实验临时生成 BGM/SFX/TTS；视频无声，字幕也不由 HyperFrames 烧录。

### 9.4 专属门槛

- doctor/lint/render 均能稳定完成；
- 4 秒 1080x1920/30 输出能完整解码并标准化；
- warm render 建议不超过 2 分钟；
- 第一个模板完成后，每个同类镜头的人工准备不超过约 10 分钟；
- designed_info 至少明显优于 FFmpeg；
- layered_environment 若需要复杂手工抠图，可降为 `manual_only`；
- narrative_character 无提升不影响其设计型结论；
- 取消后 Chromium/Node 子进程可收束，无孤儿进程；
- Apache-2.0 许可记录完整。

HyperFrames 即使通过，也只能按“设计型镜头路由”进入候选，不成为所有图片默认动态化。

## 10. Draw Things 与本地 I2V 有界实验

### 10.1 最后执行的原因

本地生成式 I2V 对 M1 Pro 的时间、内存、模型大小和稳定性风险最高，而 MVP 已有 FFmpeg 出片路径，所以它排在最后；前述工具若已覆盖主要需求，可以直接判为 `research_only`，无需下载视频模型。

### 10.2 用户授权硬门

执行者必须先报告：

- Draw Things CLI/App 当前可选安装方式；
- 拟用的一个最小、当前官方支持的 image-to-video 模型；
- 模型与依赖精确或保守估计下载量；
- 许可证、是否需要 App Store/登录、模型来源；
- 预计单次耗时、内存和磁盘上限；
- 计划只生成几个片段、最长运行多久。

只有用户明确同意后才安装/下载。不得默认安装 App、Homebrew HEAD 包或多 GB 模型；不得复用包 B Python；不得下载第二模型挽救首个失败。

### 10.3 阶梯式试验

1. CLI `--help`、版本、模型发现和取消探针；
2. 低分辨率/短帧数最小 image-to-video；
3. 若成功且资源正常，使用 portrait 或 landscape 中最适合的一张做 3–4 秒正式候选；
4. 若单片在 20–30 分钟内完成且质量可接受，再至多扩到总共 3 张以满足正式 Provider 评价；
5. 任一步超时、memory pressure 持续红色、swap 激增、模型崩溃或严重漂移即早停；
6. 保存原始帧/视频、参数、模型、seed、时间、资源和许可证；
7. 输出由 FFmpeg 标准化后再比较。

### 10.4 专属门槛

- 3–4 秒正式镜头不超过用户已确认的约 20–30 分钟；
- 一条最终短视频最多路由 1–2 个 I2V 镜头；
- 人脸、手、服装、建筑和背景不出现明显漂移；
- 首帧与输入关键帧保持可辨认连续性；
- 无严重闪烁、随机镜头切换或不可控文本；
- 失败/取消可识别，旧 FFmpeg 镜头保留；
- 模型许可证允许当前本机使用，并记录未来分发限制。

若只在一张图上成功，结论最多 `research_only`；正式候选仍须三图与用户 A/B 门。

### 11.1 实验接口

它不是正式公共 API，不进入 `models.py` 或 Schema。

### 11.2 未来正式 Provider 的最低形态

若有候选通过，计划 05/06 的接入设计至少遵守：

```text
输入：已校验关键帧 + 目标时长 + 语义意图/安全预设 + cancel_event
输出：无字幕、无项目人声的单镜头视觉文件 + 结构化结果
标准化：包 A FFmpeg 统一 1080x1920/30/yuv420p
后续：包 A 继续处理音频、字幕、缓存、时间线、final 和报告
失败：返回稳定错误，当前镜头回退 FFmpeg
```

任务包当前只有基础 motion preset/strength/intent；在未形成稳定新契约前，实验路由由 Codex/侧车决定，不扩 Schema v1。

### 11.3 缓存与版本

实验缓存键至少包括：

- 输入图哈希；
- provider/模型/工具版本；
- 受控参数预设；
- 目标时长、尺寸、FPS；
- 对 HyperFrames 还包括 composition 源哈希；
- 对 I2V 还包括 seed/模型文件摘要。

实验不得写入计划 03 的正式 `cache/manifest.json`。待工具入选后再设计正式层级，避免研究状态污染主链缓存。

## 12. 必须由用户参与的环节

### 12.1 大下载与系统安装授权

这是明确的用户参与硬门。原因不是技术上无法自动执行，而是 MFLUX/DepthFlow/HyperFrames Chromium/Draw Things 模型可能带来数百 MB 至多 GB 下载、较长占用和系统级安装。

执行批次 1 完成盘点后，应把候选的实际下载量、安装位置、磁盘上限和卸载方式汇总成一次授权请求，尽量不逐工具反复询问。用户可以：

- 同意全部隔离实验并给出总磁盘上限；
- 只同意 DepthFlow/HyperFrames，不下载本地大模型；
- 只同意 MFLUX；
- 拒绝任何大下载，此时相关候选记为 `research_only`，计划继续。

在获得授权前，仍可完成计划 03 工程债修正、Image 2、基准集、文档/许可证研究和 FFmpeg 基线。

### 12.2 最终视觉 A/B 审片

这也是必须的用户参与环节。高级动态化“是否明显更好”包含审美和眩晕/自然度判断，不能只由 probe、像素差或 Codex 自评代替。

执行者应准备：

- 不标工具名的 A/B/C 短片；
- 三图联系表和主要风险特写；
- 每个工具耗时/复杂度的简表；
- 只需用户回答“更喜欢哪版、哪些瑕疵不能接受、是否值得作为少量特殊镜头”的简短问题。

用户不需要操作命令、安装模型或填写底层参数。若用户暂时无法审片，计划最多给出 `CONDITIONAL`，不能自行宣称某个高级 Provider 已通过主观质量门。

### 12.3 不需要用户提前决定的事项

- 继续采用中文叙事插画/半写实插画作为默认测试风格；
- 三图基准类型；
- FFmpeg 对照、统一规格、技术评分和早停；
- 候选工具的实验顺序；
- 代码文件和测试的局部命名；
- 未达门槛时保留 FFmpeg 默认。

### 批次 3：MFLUX 本地图片后备

#### 目标

在得到用户下载授权后，用一个模型判断 MFLUX 是否值得保留。

#### 操作

#### 退出条件

- 三图有输出或有证据早停；

### 17.1 前置与安全硬门

- 无严重脸手、乱码、水印；
- 三图基准与 FFmpeg 对照完整；
- 本地图片后备有明确决定；
- 不把图像 API 接入包 A。

### 17.3 动态化硬门

- DepthFlow、HyperFrames 有三类/三图证据或合理早停；
- I2V 有授权后证据或明确 research_only；
- 所有实跑输出可 probe、完整解码、统一规格；
- 技术和视觉评分完整；
- 取消、残留、资源和许可有记录；
- FFmpeg 对照始终可用。

### 17.4 决策硬门

- 每个候选得到四级结论；
- formal 高级动态候选最多一个；
- 可为零；
- 路由说明清楚，不把一个工具强行用于全部镜头；
- 用户完成 A/B 主观质量门；若未完成，只能 CONDITIONAL；
- 计划 05 输入和不得破坏边界明确。

### 17.5 回归硬门

- 本计划定向测试通过；
- 计划 01/02/03 定向测试通过；
- 新增回归为 0；
- V1、包 B、Schema、计划 03 六镜 final 未被覆盖；
- 服务和磁盘状态可解释；

- **PASS**：图片主路径、候选决策、用户视觉门和回归硬门齐全，可进入计划 05；高级动态候选可以为零；

- **FAIL**：Image 2 关键帧无法形成基本一致资产、计划 03 被破坏、实验绕过安全/授权、没有 FFmpeg 对照、结果无法复核，或把未通过工具写入正式主链；不得进入计划 05。

## 18. 风险与应对

| 风险 | 预防 | 失败后处理 |
| --- | --- | --- |
| 把工具安装数量当进展 | 先写评分和早停 | 无收益即拒绝，不再下载替代模型 |
| Image 2 角色漂移 | 角色/风格参考、小步编辑、生成账 | 改环境镜头或局部修订，不无限重抽 |
| 大模型占满磁盘 | 用户总量授权、专用缓存、每批盘点 | 只清理本计划明确模型/缓存，保留证据 |
| M1 Pro I2V 过慢 | 最小模型、阶梯试验、20–30 分钟门 | research_only，继续 FFmpeg |
| DepthFlow 人物边缘撕裂 | 三类图路由、人物压力测试 | 仅环境镜头或 manual_only |
| HyperFrames 手工准备过重 | 先做模板并计时 | 只留设计型人工镜头，不作默认 |
| GPL/AGPL 影响分发 | 外部隔离、记录许可证、不复制代码 | formal 候选需后续许可专项；否则降级 |
| 高级输出规格不一致 | 原始+标准化双份、统一 ffprobe 门 | 标准化失败即不入选 |
| 测试为避扫描再次使用代码绕行 | 收窄测试到真实风险 | 正常代码+行为测试，不以字符串游戏通过 |
| 主观自评偏差 | 盲化 A/B、用户最终审片 | 用户未审只给 CONDITIONAL |
| 实验破坏正式缓存 | 独立工作区和 manifest | 删除本 run 实验产物，正式缓存不动 |
| 低影响问题耗时 | 以视觉收益、主链、资源和维护分级 | 无明显影响者记录后退出 |
