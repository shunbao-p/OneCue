# 短视频 V2 实施计划 01：Mac 基线与三镜头技术样片

> 文档性质：可直接执行的阶段计划。
>
> 上位依据：`短视频V2规划文档/短视频V2总体目标与阶段规划.md`。
>
> 本计划只负责确认当前 Mac 基线，并以最少新代码、零新增依赖完成一条原创三镜头 V2 技术样片；它不负责建设正式 V2 Schema、完整包 A V2 内核、高级动态化 Provider 或 UI。

---

## 1. 计划目标

### 1.1 核心目标

在当前 Mac 上，用真实的 Codex 图片、包 B 人声和包 A 随包 FFmpeg，完成一条约 15–30 秒、3 个镜头的竖屏技术样片，并留下可复现的输入、命令、镜头产物、技术检查和决策报告。

这条样片用于回答：

1. 现有 A+B 在当前工作树上是否仍可稳定运行；
2. Codex ImageGen 生成的三镜头关键帧是否足以形成统一叙事；
3. 包 B 按镜头生成真实人声后，能否用实际音频时长驱动镜头长度；
4. 仅凭 FFmpeg 固定运镜、字幕、硬切和包 B 人声，是否已经能得到“基本可用”的短视频；
5. 下一份正式 Schema 与接口计划需要吸收哪些实测字段和失败模式。

### 1.2 本阶段不是要证明什么

本阶段不证明最终视觉质量已经完成，也不证明 DepthFlow、HyperFrames 或本地 I2V 可用。它只证明最小主链路成立，并为后续正式设计取得真实数据。

### 1.3 成功判定

计划完成时，至少应得到：

- 一条可正常播放的 `final.mp4`；
- 3 个独立标准化镜头；
- 3 段包 B 生成的人声 WAV；
- 3 张原创关键帧及其参考图/生成记录；
- 一个薄版、明确标记为“临时实验契约”的分镜 JSON；
- 一个合并字幕文件及必要的镜头字幕文件；
- `render_report.json`、`ffprobe-report.json` 和代表帧/联系表；
- 一份执行记录，说明基线、改动、命令、结果、问题和是否允许进入计划 02。

以下是制定本计划时在当前 Mac 上只读确认的事实。执行时仍须快速复核，但不应无条件重做昂贵验证。

## 3. 范围边界

### 3.1 本计划包含

- 当前 A/B 健康状态与最小基线复核；
- 包 A、包 B 纯测试与一次真实 A+B V1 端到端回归；
- 一个原创三镜头故事、风格说明和角色参考；
- Codex ImageGen / GPT Image 2 生成参考图和三张关键帧；
- 通过包 A 现有 TTS API 按镜头调用包 B；
- 一个隔离的、零新增依赖的实验渲染脚本；
- 3 个 FFmpeg 基础动态预设；
- 简单 ASS 字幕、硬切合成和最终 H.264/AAC 输出；
- ffprobe、完整解码、黑帧/静音警告和代表帧检查；
- 样片结论与计划 02 的输入清单。

### 3.2 本计划不包含

- 正式 `project.json` / `storyboard.json` JSON Schema；
- 修改包 A 正式 `/api/generate`；
- 新建完整 `video_v2/` 生产模块；
- 包 A UI 或分镜编辑器；
- MFLUX、Draw Things、DepthFlow、HyperFrames、ComfyUI 或本地 I2V 安装；
- BGM、环境音、SFX 和相关混音；
- 口型同步；
- 包 B 模型、推理算法或音色系统重构；
- SOAR 质量模型验收；
- 十分钟渲染、十次耐久、完整发布验收或签名公证；
- 对未产生可观察不良影响的认证、自动停止或细枝末节进行专项修复。

### 3.3 低影响问题处理规则

发现问题后先判断它是否影响以下任一项：

1. 当前 A/B 基线真实性；
2. 三镜头样片能否生成；
3. 成片是否能正常观看；
4. 下一阶段的接口设计是否会被误导；
5. 用户数据、进程或工作树是否可能受损。

若均不影响，则记录在执行报告中，暂不修复。不得以顺手清理、全面重构或“让所有检查都更漂亮”为由扩大本阶段范围。

## 5. 三镜头原创样片设计

### 5.1 样片主题

暂定题目：**《风雨城门》**。

它是原创虚构短故事，不依赖外部事实核验，也不复制用户提供过的抖音参考内容。

### 5.2 视觉风格

- 中文叙事插画 / 半写实插画；
- 古城、山雨、黄昏；
- 青灰冷色为主，灯火与信物使用克制暖色；
- 电影感构图，但不追求写真人脸级精度；
- 竖屏构图，人物和核心道具位于平台 UI 与字幕安全区内；
- 图片内不得出现文字、水印、Logo 或现代物件。

### 5.3 主要角色

年轻信使，约 22 岁；黑发束起；靛青粗布衣；棕色皮革斜挎包；携带红蜡封口的信件与一枚小型青铜信物。

先生成一张角色/风格参考表，再把它作为三个镜头的参考输入。角色表与镜头图均须保留原始生成提示词和必要的修订说明。

### 5.4 镜头与旁白

| 镜头 | 叙事目的 | 包 B 文本 | 构图 | 基础运镜 |
| --- | --- | --- | --- | --- |
| `shot-001` | 建立环境与人物 | 暮色压向古城时，一名浑身湿透的信使赶到了城门。 | 古城门外广景，信使由远处进入视觉中心 | `slow_push_in` |
| `shot-002` | 揭示危机 | 他怀里的密信，只写着一句话：山洪会在今夜抵达。 | 信使半身近景，手护住红蜡密信，不显示可读文字 | `gentle_drift` |
| `shot-003` | 完成转折与收束 | 城门闭合前，守军认出了信物，第一盏警灯终于亮起。 | 城门与烽火台中远景，信使举起青铜信物，暖光亮起 | `slow_pull_out` 或 `tilt_up` |

最终文本可以在不改变三段叙事功能的情况下做轻微口语与 TTS 适配。每段仍须独立合成，不把全文一次性交给包 B。

### 5.5 图片生成预算

- 先生成 1 张角色/风格参考表；
- 再生成 3 张镜头关键帧；
- 每个镜头原则上最多进行 1 次针对性修订；
- 若修订后仍有轻微但不妨碍观看的一致性问题，保留最佳结果并记录，不无限抽卡；
- 若出现明显换人、现代物件、错误文字、大面积畸形或主体被裁切，才视为必须修订。

三镜头角色一致性不是本阶段必须“完美通过”的前置条件，它本身就是要记录的实验结果。即使一致性只达到基本可辨，仍可继续验证后半段流程。

## 6. 临时实验契约

### 6.1 定位

`storyboard.sample.json` 只用于本计划，不宣称是正式 V2 Schema。它的价值是证明哪些字段在真实样片中必要，随后作为计划 02 的证据。

### 6.2 最小字段

顶层建议仅包含：

- `sample_version`；
- `title`；
- `resolution`；
- `fps`；
- `package_a_url` 可由 CLI 覆盖；
- `voice`；
- `shots`。

每个镜头建议仅包含：

- `id`；
- `narration`；
- `image`；
- `motion_preset`；
- `focus`；
- `head_pad_sec`；
- `tail_pad_sec`；
- `caption`。

不加入 Provider Registry、复杂状态机、缓存键、I2V 参数、BGM、SFX、质量评分模型或 UI 字段。

### 6.3 验证规则

- 恰有 3 个镜头；
- 镜头 ID 唯一且符合 `shot-NNN`；
- 所有路径必须位于样片工作区；
- 图片必须存在且可由 FFmpeg 解码；
- 旁白不能为空；
- `motion_preset` 只能来自本阶段固定集合；
- `focus` 若存在，必须是 0–1 范围内的归一化坐标；
- 头尾留白必须为非负有限数；
- 未知字段可以在实验阶段明确拒绝，避免拼写错误静默生效。

## 7. 实验渲染器设计

### 7.1 命令入口

`render_sample.py` 建议接受：

```text
--job-dir
--storyboard
--package-a-url
--ffmpeg
--ffprobe
--overwrite
```

所有外部命令使用参数数组执行，不使用拼接 shell。默认不覆盖已有关键产物；只有显式 `--overwrite` 才允许重做本阶段生成文件。

### 7.2 TTS 流程

对每个镜头：

1. 调用包 A `POST /api/tts`；
2. 默认使用 `女播音.wav`、MF 推荐 4 步、`speed=1.0`、`max_pause=0.3`；
3. 轮询 `/api/status/<job>`；
4. 完成后从 `/api/tts_file/<job>` 下载 WAV；
5. 用 ffprobe 读取真实时长、采样率、声道和编码；
6. 将实际时长写入运行时报告；
7. 单段失败只重试一次，仍失败则停止本批，不生成伪造音频或替换为系统 TTS。

若 WAV 已存在、报告中的输入文本哈希和文件哈希相符，可以复用；本阶段不为此建设通用缓存框架。

### 7.3 镜头时长

```text
镜头时长 = 实际 WAV 时长 + head_pad_sec + tail_pad_sec
```

初始建议：

- `head_pad_sec = 0.15`；
- `tail_pad_sec = 0.25`。

不得通过明显变速或强行截断包 B 人声去适配预估时长。

### 7.4 基础运镜

本阶段只实现三个真正使用的预设，并保留一个 `static` 调试兜底：

- `slow_push_in`；
- `gentle_drift`；
- `slow_pull_out` 或 `tilt_up`；
- `static`。

实现要求：

- 先按竖屏安全裁切放大到足够 overscan，再做低幅度运动；
- 运动始末连续，不跳变；
- 以主体焦点约束裁切，避免脸或信物被移出画面；
- FFmpeg 输出统一为 1080x1920、30 FPS、H.264、yuv420p；
- 不启用硬件编码作为成功前提；
- 预设参数写在实验脚本的明确映射中，不从 JSON 接受任意 filtergraph。

### 7.5 字幕

- 使用包 A 随包 `simhei.ttf` 与 ASS/libass；
- 每个镜头只显示该镜头对应短句；
- 默认最多两行；
- 置于下方安全区，但不得贴近画面最底部；
- 避免大号居中字幕遮挡主体；
- 生成镜头级 ASS，同时生成一份基于最终时间线的合并 `captions.ass`；
- 第一条样片不做逐字高亮和复杂动画字幕。

### 7.6 合成

- 每个镜头先独立生成标准化 MP4；
- 正式验收路径使用硬切 concat，避免在第一条样片中让视觉叠化与独立人声时间线产生不必要耦合；
- 若硬切版完成且实现成本很低，可以额外生成一个含 0.25–0.35 秒短叠化的 `preview.mp4` 做对照，但它不是本阶段退出条件；
- 不使用 BGM、环境音和 SFX；
- 最终音频统一为 AAC、48 kHz；可输出双声道，但不得为了声道形式引入复杂音频处理；
- 不做过度响度工程。先测量并试听；只有出现明显削波、过轻或镜头间音量突变时才做最小修正。

### 7.7 报告

`render_report.json` 至少记录：

## 8. 分批实施步骤

### 批次 2：样片 Brief、临时任务包与关键帧

#### 目标

#### 退出条件

- 三张关键帧均存在且可解码；
- 无文字、水印、现代物件和严重畸形；
- 两个以上包含信使的镜头中，人物与服装至少基本可辨为同一角色；
- 即使一致性不理想，也已有明确记录且图片仍足以继续测试动态、字幕和合成。

### 批次 3：实验渲染器与自动测试

#### 目标

以最少代码建立临时分镜验证、TTS 调用、运镜、字幕、镜头标准化和报告能力。

#### 操作

1. 新增隔离实验目录、脚本和 README；
2. 先为临时契约、路径安全、预设白名单和报告结构编写针对性测试；
3. 实现 CLI 参数与任务包校验；
4. 实现包 A TTS HTTP 客户端；
5. 实现实际 WAV 时长探测；
6. 实现本阶段三个运镜预设与 `static` 兜底；
7. 实现简单 ASS 字幕；
8. 实现单镜头渲染、硬切合成和报告；
9. 所有 subprocess 使用参数数组，不使用 `shell=True`；
10. 运行新增测试和受影响的既有测试。

#### 退出条件

- 新增单元/契约测试通过；
- 临时任务包的非法路径、未知预设和空旁白会在渲染前失败；
- 脚本可在不修改 `kt_web.py`、`kt_video.py` 和包 B 源码的情况下运行；
- 无新增第三方依赖；
- 代码保持实验边界，未被正式 Web 入口导入。

### 批次 4：真实三镜头渲染

#### 目标

使用三张真实关键帧与三段真实包 B 人声生成最终样片。

#### 操作

1. 运行实验渲染器；
2. 按镜头依次提交 TTS，保存任务状态和 WAV；
3. 以实际 WAV 时长生成三个镜头；
4. 检查镜头中主体是否被运镜裁切；
5. 以硬切合成 `final.mp4`；
6. 若低成本可行，再生成短叠化 `preview.mp4`，但不得延误主样片；
7. 生成合并字幕、报告、代表帧和联系表；
8. 若某镜头失败，只重做该镜头；
9. 若高级效果不足，不在本批安装其他工具，先完成 FFmpeg 主样片。

#### 退出条件

- 3 段 TTS、3 个镜头和最终视频全部生成；
- 单镜头与最终视频符合统一技术规格；
- 旁白完整、顺序正确、字幕对应；
- 运镜可感知但不明显破坏构图；
- 任一失败和重试均被记录。

### 批次 5：技术质量门、视觉复核与结论

#### 目标

用技术证据和实际观看共同判断最小 V2 主链路是否成立，并形成计划 02 输入。

#### 操作

1. 用 ffprobe 检查各镜头和最终视频；
2. 用 FFmpeg 完整解码到 null，确认无解码错误；
3. 运行 `blackdetect`、`silencedetect` 等轻量检查，将结果作为警告而非机械硬失败；
4. 抽取每个镜头中点帧和镜头边界帧；
5. 生成联系表；
6. Codex/人工观看 `final.mp4`，按内容、图片一致性、运镜、字幕、人声和节奏记录结论；
7. 对阻塞观看的问题只允许一次镜头级修复循环；
8. 更新执行记录与 `render_report.json`；
9. 提取计划 02 必须正式化的字段、错误、状态和测试需求。

#### 退出条件

- 所有技术硬门通过；
- 视觉与听觉结论已有明确 PASS、CONDITIONAL 或 FAIL；
- FAIL 项若不阻塞最小主链路，已列入后续而非继续扩展本阶段；
- 已明确是否进入计划 02。

## 10. 验收标准

### 10.1 基线硬门

- 包 A `/api/health` 正常；
- 包 B 为 `ready`；
- 包 A 识别包 B API 为 `dots-tts.synthesize.v1` 或已有兼容路径；
- MF 真实 TTS 成功；
- 现有 V1 MP4 可生成并通过既有 25 FPS 规格检查；
- 现有工作树未被回退或清理。

### 10.2 图片硬门

- 3 张关键帧可解码；
- 无明显水印、Logo、乱码或错误文字；
- 无严重脸部、手部或结构畸形；
- 主体在竖屏安全区内；
- 至少两张角色镜头基本可辨为同一人物与同一服装。

### 10.3 单镜头技术硬门

每个 `shots/shot-NNN.mp4`：

- 恰有一路 H.264 视频和一路 AAC 音频；
- 1080x1920；
- 30 FPS；
- yuv420p；
- 音频 48 kHz；
- 时长与对应 WAV 加留白的目标差不超过 0.15 秒；
- 完整解码无错误；
- 无非预期长黑帧或整段静音。

### 10.4 最终视频技术硬门

- `final.mp4` 可被 macOS 常见播放器打开；
- H.264、1080x1920、30 FPS、yuv420p、AAC 48 kHz；
- 总时长与三个标准镜头之和误差不超过 0.25 秒；
- 完整解码无错误；
- 三段人声均存在，顺序正确；
- 字幕不越出画面；
- 报告和最终文件哈希存在。

### 10.5 基础观感门

- 成片不是黑底字幕；
- 成片不是单张图片覆盖全部音频；
- 三个镜头形成可理解的开端、危机与收束；
- 每镜运镜可感知，但不会把主体持续裁出画面；
- 字幕可读且不过度遮挡主体；
- 人声清楚，无明显断句、削波、过轻或镜头间突兀音量跳变；
- 在不使用高级动效、BGM 和 SFX 的情况下，整体达到“可以完整观看、可以继续改进”的水平。

### 10.6 结论等级

- **PASS**：技术硬门全部通过，基础观感成立，可进入计划 02；
- **CONDITIONAL**：主链路成立，但图片一致性、运镜或字幕有明确局限；记录后仍可进入计划 02，并把局限转成设计要求；
- **FAIL**：真实 TTS、镜头渲染、合成或解码等主链路无法完成；不得进入计划 02，先修复阻塞项。

## 11. 风险与应对

| 风险 | 预防 | 失败后处理 |
| --- | --- | --- |
| 现有服务被测试中断 | 先健康检查并复用；不运行生命周期停服脚本 | 只用身份验证过的启动器恢复，并记录原因 |
| 工作树既有修改被覆盖 | 开始前保存 status/diff 摘要；限定修改目录 | 停止执行，恢复本阶段自己的变更，不动用户文件 |
| ImageGen 人物不一致 | 先角色表，再以同一参考输入生成三镜头 | 每镜最多一次修订；仍不完美则记录并继续 |
| 图片竖屏裁切破坏主体 | 生成时留安全区；运镜使用低幅度和焦点 | 只调整该镜头焦点/强度，不重做全部素材 |
| 包 B 合成较慢 | 使用 MF、短句、逐镜头执行 | 单段重试一次；不切换 SOAR，不伪造音频 |
| TTS 时长与预估不同 | 以 WAV 实际时长生成镜头 | 调整镜头留白，不拉伸人声 |
| FFmpeg concat 兼容失败 | 所有单镜头先统一规格 | 检查 timebase/帧率/像素格式，修实验标准化步骤 |
| 字幕字体或路径问题 | 使用随包 simhei.ttf，参数数组执行 | 复用 `kt_video.stage_render_assets` 的思想或复制最小安全做法，不改旧渲染器 |
| 实验脚本开始膨胀 | 只实现本次需要的字段和三个预设 | 将扩展需求记录到计划 02/03，不在本阶段继续抽象 |
| 低影响告警占用时间 | 用五项影响判断规则分级 | 记录为非阻塞，不立即修复 |
